# Self-review: what does not work yet

Each item states what fails, why, its impact in production, and how it would be fixed. Measured, not guessed:
the numbers come from `evals/results/` and `scripts/acceptance.py`.

| # | Limitation | Why | Impact in production | Fix |
|---|---|---|---|---|
| L-1 | **"Transaction declined" has no official Getnet explanation in the corpus** | none of the 29 public sources describes decline codes (measured: 0 chunks) | the reply explains the decline from the issuer's response code returned by the backend, and offers a human for anything beyond it | ingest Getnet's internal decline-code table, or expose it as a support tool |
| L-2 | **Holidays are not modelled** in deposit dates | the simulated backend skips weekends only | a deposit date can be one day early around a national holiday | read business days from the settlement system (or a holiday calendar) instead of computing them |
| L-3 | **Multilingual retrieval uses a small embedding model** (MiniLM, 384 dims) | chosen so RAG runs locally with no key and the image stays at ~400 MB | English questions over a Portuguese corpus rely on full-text matching of product names; Recall@5 is 1.0 and MRR@10 0.79 on 20 gold queries (7 topics, PT and EN, each anchor verified against the corpus) | a larger multilingual model or a hosted embedding API, and more gold queries with per-topic recall |
| L-4 | **The ingest service re-fetches all sources on every start** | idempotent and simple; ~45 s for 29 sources | slower restarts; a site outage falls back to snapshots, never to an empty index | schedule ingestion separately and skip sources whose content hash did not change |
| L-5 | **The operator side is an API, not a screen** | out of scope for the challenge | operators need a client to list cases, reply and approve | a small operator console on top of `/operator/*` |
| L-6 | **Demo passwords are kept in the database in demo mode** | so every replica shares them and `make creds` can print them | none in production: `APP_MODE=production` creates no demo users | — (by design; production users come from the identity provider) |
| L-7 | **Login attempts are never pruned** | the throttle only counts the last 15 minutes; history is kept for audit | the table grows slowly | a retention job (e.g. 90 days) |
| L-8 | **The fake model writes extractive answers** | it exists so tests and the keyless demo run the real graph | without a key, answers are correct but stitched from sources, not conversational | use any real provider via `LLM_PROVIDER` |
| L-9 | **Cost is an estimate** from a per-token price in settings | prices differ by model and change | `llm_cost_usd_total` is indicative | read prices per model from configuration managed with the provider contract |
| L-10 | **Grounding verifies figures, not claims** | a deterministic word-level entailment check tends to delete correct sentences too; comparing meaning reliably needs a model | by choice, word-level claims are left to the LLM judge, which catches them: it flagged attributing an action to a person, relabeling a product, and extending a feature across products, and the reply prompt (1.3.0) now forbids all three — faithfulness rose to 0.964–1.0 across the three committed Opus runs | a claim-level entailment check with a model in the turn for high-risk intents (costs tokens per turn), or few-shot "say only what the source says" examples |
| L-11 | **The plan is fixed at the start of the turn** (≤ 2 agents) | one structured planning call keeps cost and latency predictable | if the router plans only Support for "my machine is offline", the manual's reconnection steps are not consulted | let an agent hand off to another (a "consult knowledge" tool) or add a bounded re-plan edge after each agent |
| L-12 | **Waiting for an approval holds a request thread** (up to `HITL_SYNC_WAIT_S`) | a synchronous reply is simpler for a chat client | under load, long windows tie up workers; a late approval is still executed and posted | resume through LangGraph `interrupt` and stream the outcome, or keep the window short |
| L-13 | **PII redaction is pattern-based** | CPF, CNPJ, cards (Luhn), emails and phones have reliable shapes | names and street addresses are not redacted | add a named-entity model for Portuguese in `app/security/redact.py` |
| L-14 | **Demo is the default mode; production has no user-provisioning path** | the challenge must run with one command and no setup | production users must come from somewhere else | delegate identity to an OIDC provider and validate its tokens instead of local passwords |
| L-15 | **Some official pages carry little content** (an unrendered template on one product page, a maintenance notice on another) | the site itself; the extractor drops `{{…}}` placeholders | those questions lean on the manuals and FAQ | add the help-center articles linked from the FAQ pages as sources |
| L-16 | **No overall per-turn deadline** | each model call has a timeout and retries | a slow provider can make one turn take several call-timeouts | a turn-level deadline that answers with what was gathered |
| L-17 | **The token budget is soft** | it is checked between model calls; a call in flight cannot be cut | a turn can end above the budget (measured up to ~37k tokens with Opus against 24k); the response says `over_token_budget` | derive each call's `max_tokens` from what is left and add a turn deadline |
| L-18 | **`/chat` has no per-user rate limit or quota** | login is throttled; chat is not | one user can drive model cost up | a per-user request and token quota in the shared database, like the login throttle |
| L-19 | **The real-model evaluation used the Claude Code CLI path** | no API key was available while building | tool calls were requested as structured output, not the API's native tool use in `app/llm.py` | run `LLM_PROVIDER=anthropic python -m evals.run --judge` with a key, three times, and commit the results |
